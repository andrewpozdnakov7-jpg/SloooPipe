# Сборка SloooPipe из ZIP в WSL

Для новой основы ZIP 13 используйте builder revision 08. Главный NewPipe теперь
использует Gradle 9.8.2 / AGP 9.4.1 / Kotlin 2.4.21; подробности —
[текущая основа](../docs/CURRENT_UPSTREAM_BASE.md). Нижняя планка ниже сохранена
для совместимости скрипта со старыми архивами и отдельным NewPlayer.

Скрипт `build-slooopipe-from-source-zip-wsl.sh` запускается на основном компьютере
в Ubuntu WSL. Здесь он подготовлен по статическому анализу исходников;
сборки, unit-тесты и воспроизведение на этом компьютере не запускались.

## Размещение

Скопируйте скрипт в `~/projects/slooopipe-src/`.
Путь из Windows: `\\wsl$\Ubuntu-26.04\home\<linux-user>\projects\slooopipe-src`.

```text
slooopipe-src/
  build-slooopipe-from-source-zip-wsl.sh
  sources/        ZIP с исходниками
  signing/        существующие ключи от Slooop
  offline-maven/  переносимые зависимости JitPack (если предоставлен набор)
  work/           распакованные рабочие копии, отдельно по SHA-256
  out/run-*/      результаты каждого запуска
```

Скрипт по умолчанию использует `$HOME/projects/slooopipe-src`, независимо от
текущего каталога. Другой путь задаётся через `--base-dir` либо
`SLOOOPIPE_BASE_DIR`. В `sources` кладутся ZIP, а не распакованные проекты.
Сам скрипт и эту инструкцию не нужно помещать в `sources`.

## Ключи: те же, что у Slooop

Используется каталог `slooopipe-src/signing`.
Схема свойств повторяет предоставленный скрипт Slooop:

```properties
store.file=имя-существующего-ключа.jks
store.password=пароль-хранилища
key.alias=существующий-alias
key.password=пароль-ключа
```

Сохраните реальные настройки в `signing/keystore.properties`; значения из
примера нужно заменить. Относительный `store.file` считается от `signing`,
абсолютный Linux-путь также поддерживается. Пароли передаются `apksigner`
через переменные окружения внутри отдельного процесса, не в аргументах команды.

Если `keystore.properties` отсутствует, скрипт, как исходный Slooop builder,
ищет **уже существующий** `signing/dashchan2-local-debug.keystore` и использует
его прежние значения: alias `androiddebugkey`, пароли `android`.
Новые ключи скрипт не создаёт. Отсутствующий ключ/неверные настройки — ошибка.
Секреты не включаются в ZIP и Git.

## Окружение основного компьютера

- Bash 4+, Python 3.9+, JDK **21** (`java`, `javac`, для APK также `keytool`).
  Более новый JDK допускается при совместимости с выбранным Gradle;
  для объявленного в проектах `jvmToolchain(21)` должен быть доступен JDK 21.
- Git, `flock`, стандартные Linux-инструменты (`sha256sum`, `find`, `sort`,
  `realpath`, `sed`, `tee`, `mktemp`).
- Linux Android SDK: `ANDROID_HOME` или `ANDROID_SDK_ROOT`.
  Без этих переменных проверяются `$HOME/android-sdk` и `$HOME/Android/Sdk`.
- Для подготовленных рабочих копий обоих проектов нужен SDK **37**
  (`platforms/android-37.0/android.jar`, пакет `platforms;android-37.0`)
  и Build Tools **36.0.0**.
  Скрипт читает эти требования из файлов выбранного проекта.
- Для APK нужны установленные стабильные Android Build Tools с
  `apksigner`, `zipalign`, `aapt`; выбирается самая новая полная установленная
  версия. Инструменты и платформы автоматически не устанавливаются.
- Для JVM UI-тестов модуля `shared` нужен рабочий X-дисплей WSLg (`DISPLAY`)
  либо установленные `xvfb-run`, `Xvfb` и `xauth`. Без `DISPLAY` скрипт
  использует `xvfb-run -a`. Пропускать эти тесты под видом успеха он не будет.

При необходимости перед запуском задайте `JAVA_HOME` для JDK 21 и `ANDROID_HOME`
для установленного SDK. Системный Gradle не нужен: каждый проект использует
свой Wrapper. Скрипт проверяет нижнюю планку Slooop: Gradle 9.6.1,
AGP 9.4.0, compileSdk 37 и Build Tools 36.0.0. Более новые версии в исходниках
допускаются; понижения или скрытого переписывания настроек скриптом нет.

В подготовленных рабочих копиях:

| Проект | Gradle | AGP | Kotlin |
| --- | --- | --- | --- |
| NewPipe (основа refactor) | 9.6.1 | 9.4.0 | 2.3.21 |
| NewPlayer | 9.6.1 | 9.4.0 | 2.3.21 |

Kotlin/Compose-компилятор, KSP 2.3.8 и Hilt 2.59.2 NewPlayer выровнены с
NewPipe-refactor. Slooop в рассмотренном checkout не задаёт версию Kotlin Gradle
Plugin, поэтому для Kotlin использована существующая версия основного NewPipe.
Зависимости, не относящиеся к этой миграции, пока имеют версии своих проектов.

Исходные ZIP из `01 start` имеют более старые Gradle/AGP и не пройдут новую
проверку. Для сборки используйте подготовленный ZIP из папки `03 delivery`.

Первый запуск Wrapper/Gradle обычно требует доступ к репозиториям зависимостей.
NDK, ABI-меню, сборка FFmpeg, dav1d и расширений Dashchan в этот скрипт не перенесены:
в рассмотренных настройках этих двух проектов такой сборки нет.

## Запуск

```bash
cd ~/projects/slooopipe-src
bash ./build-slooopipe-from-source-zip-wsl.sh
```

Меню предлагает NewPipe, NewPlayer test-app или оба проекта; затем/перед этим
выбирается операция: APK, APK + unit-тесты, APK + unit-тесты с подробным логом
или только unit-тесты. Если подходящий ZIP один, он выбирается автоматически.
Если несколько — скрипт спрашивает номер.

Команда без меню для NewPipe:

```bash
bash ./build-slooopipe-from-source-zip-wsl.sh \
  --component main --operation build-test \
  --newpipe-zip './sources/SloooPipe-sources-20261020-02.zip'
```

Оба проекта из одного подготовленного архива:

```bash
bash ./build-slooopipe-from-source-zip-wsl.sh \
  --component both --operation build-test-log \
  --newpipe-zip './sources/SloooPipe-sources-20261020-02.zip' \
  --newplayer-zip './sources/SloooPipe-sources-20261020-02.zip'
```

Допускается единый ZIP с обоими проектами: укажите один и тот же файл для двух
аргументов. Архив распакуется один раз. Корни определяются по файлам модулей,
а не по имени ZIP; неоднозначные архивы с двумя NewPipe-проектами отклоняются.
Файлы NewPipe-dev из референсов тоже распознаются как NewPipe: основой этого
проекта остаётся refactor. Сборка `both` остаётся двумя независимыми
сборками; подключение NewPlayer к приложению этим скриптом не реализуется.

## Что выполняется

NewPipe:

```text
:app:assembleDebug
:app:testDebugUnitTest           если выбраны тесты
:shared:jvmTest                 если выбраны тесты и есть модуль shared
```

NewPlayer:

```text
:test-app:assembleDebug
:new-player:testDebugUnitTest    если выбраны тесты
:test-app:testDebugUnitTest      если выбраны тесты
```

В режиме `test` задачи `assembleDebug` не вызываются, APK и подпись не нужны.
Сами unit-тесты могут компилировать код приложения и зависимости.
Android host-тесты KMP `shared`, инструментальные тесты на устройстве,
lint и воспроизведение этот скрипт не запускает.

Выбран вариант `debug`: он не требует релизной подписи внутри Gradle.
Полученный APK выравнивается и переподписывается **вашим существующим ключом**,
после чего проверяется `apksigner`. Тип сборки от переподписи остаётся debug.
Названия приложений и applicationId остаются заданными исходниками;
брендинг SloooPipe этим скриптом не вносится.

В распакованной копии нормализуется только `gradlew` (LF и разрешение запуска),
создаётся `local.properties` с Linux SDK-путём и локальный Git с пустым коммитом
на ветке `dev`. Git нужен, потому что NewPipe читает имя ветки при конфигурации
Gradle; ожидаемый исходный пакет приложения — `org.schabi.newpipe.debug`.
Git из исходного ZIP не переносится; исходные Kotlin/Java/Gradle-файлы скрипт
не исправляет. Публикации на GitHub нет.

## Кэш и результаты

Исходный ZIP сохраняется. `work` сохраняется после успеха и после ошибки:
повторный запуск того же ZIP использует тот же каталог по полному SHA-256.
Другой ZIP с другим содержимым получает другую рабочую копию.
`--fresh` создаёт новую распаковку, не удаляя старую. В пределах запуска оба
компонента одного ZIP используют одну распаковку. По умолчанию кэш требует,
чтобы файлы `work` не редактировались вручную; для чистой проверки нужен `--fresh`.

Сборки Slooop и SloooPipe имеют разные рабочие папки. С ревизии 04 Gradle User
Home по умолчанию общий: берётся существующий `GRADLE_USER_HOME`, а без него
`$HOME/.gradle`, как в исходном скрипте Slooop. Это позволяет повторно использовать
уже скачанный Gradle 9.6.1 и совпадающие зависимости. Точную другую папку можно
задать через `--gradle-user-home DIR` или `SLOOOPIPE_GRADLE_USER_HOME`.
Два SloooPipe-запуска в одном базовом каталоге блокируются `flock`, чтобы не
изменять один work одновременно. Общие JDK/Android SDK не изменяются скриптом.

Каждый запуск создаёт новый `out/run-*`, содержащий:

- `BUILD_INFO.txt`: выбранные архивы, их SHA-256, объявленные версии и команды;
- `build-main.log` / `build-player.log`: полные выводы Gradle;
- `system-before.log`, `STATUS.txt`, при ошибке `system-after-failure.log`;
- `UNIT_TESTS-*.txt` и `reports/`: результаты реально запрошенных unit-тестов;
- `apks/main/`, `apks/player/`: подписанные APK, вывод проверки сертификата,
  метаданные пакета;
- `SHA256SUMS.txt`: SHA-256 готовых APK после успешной сборки всех компонентов.

Перед тестами удаляются только сгенерированные тестовые XML/HTML в рабочей
копии. Тестовые задачи принудительно выполняются заново без использования их
старых результатов из build cache; кэш компиляции сохраняется. Отсутствующие
JUnit XML, только skipped-тесты и пустые обязательные наборы не считаются
успешной проверкой. Для `test-app`, где в переданном снимке unit-исходников
нет, это отмечается отдельно, без заявления об успехе его тестов.

Если ошибка произошла в одном проекте, последующие шаги останавливаются;
логи и рабочая копия остаются. Для разбора передавайте папку текущего `out/run-*`.
Успешная сборка и unit-тесты не подтверждают воспроизведение.

## Исправление пути SDK 37 (ревизия скрипта 20261020-03)

Официальный пакет Google называется `platforms;android-37.0`, каталог —
`platforms/android-37.0`. Прежняя проверка `android-37` в ревизии 02 была ошибкой.
ZIP исходников `SloooPipe-sources-20261020-01.zip` можно оставить:
для исправления этой проверки достаточно заменить внешний WSL-скрипт.

Прямой официальный архив:
[platform-37.0_r02.zip](https://dl.google.com/android/repository/platform-37.0_r02.zip),
67 281 901 байт; SHA-1 из официального каталога Google:
`ed8ebf7f8822a4de5686d427f237d2fa30ff7410`.
Внутри архива корневая папка `android-37.0`; распаковка выполняется в
`~/android-sdk/platforms/`, чтобы `android.jar` оказался в
`~/android-sdk/platforms/android-37.0/android.jar`.
Каталог пакетов: https://dl.google.com/android/repository/repository2-3.xml.

## Повторное использование Gradle Slooop (ревизия скрипта 20261020-04)

Старые ревизии принудительно назначали `slooopipe-src/cache/gradle` и поэтому
Wrapper не видел дистрибутив из обычного кэша Slooop. Теперь используется
существующий общий Gradle User Home, обычно `~/.gradle`.
Старый отдельный кэш не удаляется и не копируется поверх общего.

Версия определяется Wrapper каждого проекта и по-прежнему равна 9.6.1:
автоматического перехода на старую версию из кэша нет. Если нужный дистрибутив
в общем кэше отсутствует, Wrapper всё ещё попробует скачать его.
Новые зависимости, которых не было у Slooop, также могут требовать сети.

Явный выбор обычного кэша в WSL:

```bash
bash ./build-slooopipe-from-source-zip-wsl.sh --gradle-user-home "$HOME/.gradle"
```

Из PowerShell:

```powershell
wsl.exe -d Ubuntu-26.04 -- bash -lc 'cd ~/projects/slooopipe-src && bash ./build-slooopipe-from-source-zip-wsl.sh --gradle-user-home "$HOME/.gradle"'
```

В начале запуска должны быть ревизия `20261020-04-shared-gradle-cache` и строка
`Gradle user home: ~/.gradle`.

## Локальные зависимости JitPack (ревизия скрипта 20261020-05)

После сетевого тайм-аута JitPack подготовлен отдельный набор семи **уже
объявленных** зависимостей основного NewPipe. Их версии и исходники приложения
не меняются. В него включены оригинальные POM, Gradle Module Metadata и JAR/AAR
из `https://jitpack.io/`, а также `mirror-manifest.json` с SHA-256 и URL каждого
файла. Полный список координат находится в манифесте.

`SloooPipe-jitpack-offline-20261020-01.zip` распаковывается непосредственно
в `~/projects/slooopipe-src`: он добавляет `offline-maven/`, обновляет
внешний скрипт и добавляет инструкцию. Основной ZIP исходников остаётся прежним.

Скрипт автоматически проверяет все файлы `offline-maven` по манифесту и создаёт
Gradle init script текущего запуска. Через settings-level `exclusiveContent`
семь конкретных модулей направляются только в локальный Maven. Это исключает
попытки скачать именно эти координаты из недоступного JitPack. Проектные
settings.gradle.kts и исходники в распаковке не переписываются.

Другая папка задаётся через `SLOOOPIPE_LOCAL_MAVEN_REPO`. Если локального набора
нет, остаётся прежнее поведение с сетевыми репозиториями. Если набор есть,
но повреждён или неполон, запуск останавливается до Gradle.

Набор не является полным офлайн-кэшем всех проектов: отсутствующие зависимости
Google Maven, Maven Central, Clojars или Gradle-плагинов могут потребовать
отдельного переноса. Документационные sources/javadoc-артефакты в набор не входят.
Выполнение Gradle с этим набором и тесты проверяются на основном компьютере.

Для повторной подготовки набора на компьютере с доступным интернетом:

```text
python tools/prepare-jitpack-mirror.py --catalog NewPipe/gradle/libs.versions.toml --output NEW/offline-maven
```

Этот вспомогательный инструмент требует Python 3.11+, получает уже объявленные
версии из TOML и скачивает готовые артефакты; Gradle и компиляторы не запускает.
Нужна новая или пустая папка назначения. Перед использованием набор должен
содержать итоговый `mirror-manifest.json`.

## Первое падение JVM-теста и исходный ZIP 02

Пользовательский запуск с локальным Maven дошёл до Kotlin-компиляции `shared`,
Android-ресурсов и запуска `shared:jvmTest`. Из семи JVM-тестов один завершился
ошибкой: `TopAppBarTest.testTopAppBarCanHaveNavigation`, ResourceEnvironment.kt:101.

Статический анализ выявил отсутствие базовой строки `app_name`: она имелась
лишь в нескольких локализованных файлах, а тест использовал `Res.string.app_name`.
В исходный ZIP 02 добавлено базовое значение `NewPipe` в
`shared/src/commonMain/composeResources/values/strings.xml`. Тест не пропускается
и его проверки не ослабляются. Результат исправления подтвердит следующий
запуск на основном компьютере.

Внешний скрипт ревизии `20261020-06-full-test-errors` дополнительно включает
полный вывод исключений, причин и stack trace для неуспешных тестов. Это даёт
больше данных непосредственно в build-main.log/build-player.log.

Обновление `SloooPipe-test-resource-fix-20261020-01.zip` распаковывается в базовую
папку `slooopipe-src`: внутри новый внешний скрипт и
`sources/SloooPipe-sources-20261020-02.zip`. Локальный Maven, SDK и signing
продолжают использоваться из существующих папок. Для обеих компонент выбирайте
исходный ZIP **02**. Его новый SHA-256 создаст отдельную рабочую распаковку.

В Windows-примерах `<linux-user>` замените именем пользователя своего WSL-дистрибутива.
