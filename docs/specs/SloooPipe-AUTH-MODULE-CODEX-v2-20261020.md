# SloooPipe: отделяемый модуль авторизации на основе PipePipe — ТЗ для Codex

Дата: 2026-10-20. Версия: 2. Учитывает уточнение пользователя об обязательной модульности и доноре PipePipe.
Основание: пользователь явно добавил требование входа в YouTube для работы в сети, где анонимное получение видео завершается отказом / требованием подтвердить, что пользователь не бот.

## Изменение цели

Основная цель сохраняется: интегрировать NewPlayer в выбранную актуальную основу NewPipe, сохранить сценарии приложения и подготовить проверяемые изменения.

Дополнительная обязательная цель: предоставить необязательный вход в YouTube и использовать полученную сессию при получении данных и воспроизведении. Пользователь должен иметь возможность смотреть видео с собственной сессией аккаунта, а также выйти и продолжить анонимно.

Требование означает восстановление доступа и воспроизведения там, где авторизованный путь действительно работает. Простое удаление надписи о блокировке, подмена ошибки пустым списком или бесконечные повторные запросы задачу не решают. Вход не гарантирует снятия сетевой блокировки, регионального ограничения или отказа со стороны YouTube.

Этот документ заменяет прежние утверждения PROJECT_GOAL.md и NEWPLAYER_INTEGRATION_REVIEW.md о том, что авторизация не включена в цель. Само предыдущее исследование остаётся полезным. Актуализировать эти документы в рабочем репозитории при применении дополнения.

## Проверенный источник для переноса

Донор реализации авторизации — PipePipe, как прямо указал пользователь. Проверены реальные исходники. Целевое приложение по ранее принятому плану — NewPipe; это задание не переключает его основу целиком на PipePipe.

- PipePipeClient: https://github.com/InfinityLoop1308/PipePipeClient
- Зафиксированная ревизия dev: `24db7c535d82edf1af30d1cdb201b51f21c1a48d`.
- PipePipeExtractor: https://github.com/InfinityLoop1308/PipePipeExtractor
- Зафиксированная ревизия main: `73442076c671ae09bd5c0f9635932a5a67bdd609`.

Референсы в PipePipeClient:

- `app/src/main/java/org/schabi/newpipe/views/YouTubeLoginWebViewActivity.java`: вход на сайт YouTube в WebView, получение cookies, перехват параметра pot из запроса воспроизведения.
- `app/src/main/java/org/schabi/newpipe/views/BaseLoginWebViewActivity.java`: базовый экран WebView.
- `app/src/main/java/org/schabi/newpipe/settings/YouTubeAccountSettingsFragment.java`: результат входа, выход, инвалидирование PO-токена.
- `app/src/main/java/org/schabi/newpipe/settings/BaseAccountSettingsFragment.java`: обновление состояния сервиса и очистка InfoCache после смены сессии.
- `app/src/main/java/org/schabi/newpipe/util/ServiceHelper.java`: передача сессии и дополнительных токенов сервису Extractor.
- `app/src/main/java/org/schabi/newpipe/App.java`: reconcileYoutubePlayerClient; при наличии cookies выбирается MWEB.
- `app/src/main/java/org/schabi/newpipe/youtube/LocalDomPoTokenProvider.kt`: дополнительная зависимость, которую нужно исследовать вместе с авторизованным путём.

Референсы в PipePipeExtractor:

- `extractor/src/main/java/org/schabi/newpipe/extractor/services/youtube/YoutubeParsingHelper.java`: addLoggedInHeaders / getAuthorizationHeader, Cookie и Authorization.
- `extractor/src/main/java/org/schabi/newpipe/extractor/services/youtube/extractors/YoutubeStreamExtractor.java`: MWEB, PO-токены, ошибки доступа и построение SABR-источников.

Установленный факт: это несколько компонентов приложения и изменённого Extractor, а не готовая независимая AAR-библиотека. Нельзя считать задачу закрытой после копирования Activity входа.

Текущий PipePipe связывает авторизованный MWEB-путь с механизмами получения источников, включая SABR. Проверить, какие источники возвращаются для выбранных тестовых видео. Если для рабочего авторизованного пути требуется SABR, включить необходимую поддержку в границу задачи или явно зафиксировать незакрытый блокер. Наличие cookies само по себе не превращает SABR в обычный progressive/DASH URL.

При переносе сохранять лицензионные уведомления и авторство; перечислить заимствованные файлы, исходные SHA и внесённые изменения. Не заменять весь Extractor без разбора: это может затронуть существующие сервисы и адаптер NewPlayer. При необходимости выделить минимальный поддерживаемый fork Extractor с фиксированной ревизией. Если выбранный путь PipePipe не работает в целевой среде, зафиксировать конкретную причину; не заменять донора молча.

## Обязательная модульность

Сделать настоящий отдельно подключаемый Gradle-модуль реализации авторизации на основе PipePipe. Изолированного пакета внутри app и переключателя в настройках недостаточно.

Цель отделения: возможность собрать приложение без реализации авторизации, независимо подключить NewPlayer и отдельно предложить интеграцию плеера исходной команде. Отключение авторизации не должно требовать удаления кода плеера или ручной правки множества экранов.

Рекомендуемая минимальная структура; названия можно адаптировать к репозиторию:

| Компонент | Ответственность | Граница зависимостей |
| --- | --- | --- |
| `:youtube-auth-api` | Небольшой контракт сессии и состояния, результат входа, события смены/очистки сессии | Не зависит от NewPlayer, Extractor, app.R, экранов и БД приложения |
| `:youtube-auth-pipepipe` | Реализация входа/выхода на основе PipePipe, собственные ресурсы, WebView, защищённое хранение сессии | Зависит от контракта; не зависит от NewPlayer и внутренней структуры app |
| Приложение и адаптер получения данных | Подключение UI входа, использование сессии в допустимых запросах Extractor, инвалидирование кешей, преобразование источников | Общий код зависит от контракта; конкретную реализацию выбирает точка сборки/DI |
| `:new-player` и его host-адаптер | Воспроизведение, MediaItem / MediaSource.Factory, интеграция с очередью и историей NewPipe | Не зависят от конкретного модуля авторизации или его UI |

Не создавать дополнительные слои только ради количества модулей. Мост к Extractor может быть небольшим отдельным адаптером/variant source set. Авторизация и воспроизведение должны иметь самостоятельные границы и коммиты.

Контракт должен позволять предоставить анонимную реализацию `NoAuthSessionProvider` без зависимости от модуля PipePipe. Его точная сигнатура — решение Codex после чтения кода; не экспортировать CookieManager, глобальные настройки PipePipe или объекты его UI в общий код. Секреты передавать только ограниченному сетевому адаптеру, а не делать частью общедоступного состояния UI.

В модуль авторизации не включать плеер, очередь, историю, скачивание и общие настройки приложения. Зависимости от политики сети, места хранения и необходимых host-событий передавать явно. Самостоятельный UI входа может использовать Activity/Fragment Android и собственные ресурсы; он не должен импортировать конкретные Activity/Fragment приложения.

### Проверяемое физическое отделение

Предусмотреть два варианта сборки или build-property с эквивалентным результатом:

- `withAuth`: подключён `:youtube-auth-pipepipe`, вход и авторизованное получение видео доступны;
- `withoutAuth`: реализация PipePipe не включена в settings/dependencies и classpath; предоставлен анонимный контракт; приложение и NewPlayer собираются и работают без входа.

Приёмка требует реально собрать оба варианта. Одного `enabled=false` при оставшейся обязательной зависимости недостаточно. Дать точные команды включения и отключения, список затрагиваемых файлов и подтверждение отсутствия реализации в dependency graph варианта без входа.

Если авторизованный путь требует PipePipeExtractor, держать его специфичные вызовы в соответствующем адаптере/варианте. Для отделяемого основного варианта предусмотреть обычный NewPipeExtractor и адаптер без входа. У PipePipeExtractor и NewPipeExtractor совпадают многие имена классов: не подключать обе реализации одновременно в один runtime classpath. Приложение вне адаптера не должно вызывать методы, существующие только в PipePipeExtractor.

PO-токены относятся к получению данных, а не к самому факту входа. Анонимный NewPipe тоже может нуждаться в своей реализации PO-токенов. Удаление auth-модуля не должно случайно удалить анонимный механизм. Если часть токенизации у донора общая, выделить необходимый контракт/адаптер и описать владельца состояния.

SABR — отдельная зависимость тракта получения/воспроизведения, а не функция формы входа. Если он нужен для рабочего авторизованного пути, разместить поддержку в backend/MediaSource-адаптере с отдельной границей. Не встраивать аккаунты в универсальный NewPlayer и не объявлять архитектурную отделяемость доказательством поддержки SABR.

Поток данных: выбранное видео → сессия через контракт / анонимный режим → адаптер Extractor → описание источников → MediaItem / MediaSource.Factory → NewPlayer.

После успешного входа повторить выбранное действие с новой сессией. Повторный запрос должен быть ограничен и связан с текущим выбранным видео. Быстрое открытие A → B не должно позволять запоздалому ответу A заменить B.

## Поведение входа и сессии

- В настройках: «Войти в YouTube», состояние сессии и «Выйти».
- После распознанного требования входа — действие «Войти» и возможность повторить получение выбранного видео.
- Наличие произвольной cookie или одной строки SID не является достаточным доказательством работающего авторизованного извлечения. Проверить сессию фактическим запросом получения данных.
- При смене аккаунта / входе / выходе инвалидировать связанные кеши ответов, источников и PO-токенов. Не смешивать данные и источники разных сессий.
- После выхода удалить сохранённую сессию и соответствующие данные WebView; следующий запрос не должен отправлять прежние credentials.
- Обрабатывать отмену входа, истёкшую/отозванную сессию и отказ самого Google принять выбранный способ входа.
- Если Google не позволяет войти в WebView, не имитировать успех. Проверить поддерживаемую альтернативу; обычный Custom Tab не предоставляет приложению cookies другого браузера автоматически. При необходимости отдельно реализовать явный пользовательский импорт cookies.
- Не добавлять в этот этап подписки аккаунта, лайки, комментарии и синхронизацию YouTube: для текущей цели достаточно сессии получения видео.

Хранить cookies/токены в приватном защищённом хранилище приложения, исключить их из обычных бэкапов, отчётов и логов. Не собирать пароль собственным полем приложения. Не передавать cookies на произвольные адреса, в сторонние сервисы или на любой googlevideo-host автоматически; правила передачи должны соответствовать конкретному запросу, домену и перенаправлениям.

## Ошибки и восстановление

Различать по доступным фактам:

- запрос на вход / подтверждение пользователя;
- недействительную или истёкшую сессию;
- сетевой отказ / rate limit;
- недоступное, приватное или ограниченное видео;
- истёкший URL потока;
- ошибку воспроизведения NewPlayer.

Не ставить диагноз «бан IP» только по любому HTTP 403. Если авторизация не устранила отказ, показать реальную причину и сохранить диагностическую категорию без секретов. Для отказов не вводить циклы бесконечного входа или перезапросов. Использовать ограниченные повторы и backoff там, где повтор оправдан.

Авторизованный запрос и последующее воспроизведение должны использовать согласованную сетевую конфигурацию. При уже настроенном пользователем proxy сохранить её согласованность между слоями. Добавление нового proxy/VPN-сервиса не включено в это задание.

## Порядок работ

1. Сначала извлечь из PipePipe минимальный набор компонентов входа и необходимых связей с Extractor. Составить короткую карту зависимостей, реализовать контракт, auth-модуль и анонимное подключение. Уже выполненные исправления сборки и исследование NewPlayer сохранить в отдельной истории изменений.
2. Доказать отделяемость двумя сборками приложения: с реализацией PipePipe и без неё. В варианте с входом проверить реальный запрос Extractor и воспроизведение через доступный на этом этапе плеер; не выдавать наличие cookies за успешный доступ к видео.
3. Затем продолжить интеграцию свежего NewPlayer по этапам A/B1 принятого плана. Авторизация должна подавать сессию через уже существующую границу, без изменений внутри NewPlayer.
4. Проверить оба варианта уже с NewPlayer: анонимное и авторизованное воспроизведение, нужные источники, вход/выход, ошибки и быструю смену видео. Не удалять старый playback path раньше проверки нового.
5. Передать отдельно изменения модуля авторизации, адаптера/Extractor и интеграции плеера. Обновить PROJECT_GOAL.md и матрицу общего плана с новым порядком и требованиями.

Не нужно ждать реализации всей очереди, Android Auto и прочих поздних этапов, чтобы проверить модуль авторизации. Не заменять эту работу ещё одним большим исследованием: следующий результат должен содержать исходники модуля, подключение и команды проверки.

Сборку, Gradle и проектные тесты выполнять на основном компьютере пользователя в WSL согласно существующему распределению работ. Если текущая среда Codex не предназначена для сборки, подготовить точные команды и не объявлять проверки успешными без лога. Для изменённых границ нужны содержательные проверки: смена/очистка сессии, доменные ограничения передачи cookies, инвалидирование кеша и отсутствие позднего запуска A после B. Матрицу устройства проходить по мере готовности соответствующей функции.

## Приёмка

| Сценарий | Ожидаемый результат |
| --- | --- |
| Реализация auth-модуля исключена из сборки | Приложение собирается с анонимным провайдером; в dependency graph нет реализации PipePipe |
| Модуль авторизации подключён, NewPlayer ещё не интегрирован | Вход и реальный запрос Extractor не требуют NewPlayer |
| NewPlayer подключён, модуль авторизации исключён | Плеер и приложение собираются; доступное публичное видео воспроизводится анонимно |
| Оба компонента подключены | Авторизованный источник передаётся в NewPlayer через host-адаптер |
| Без входа, доступное публичное видео | Анонимное извлечение и воспроизведение через NewPlayer |
| Вход и перезапуск приложения | Сессия доступна, реальный запрос подтверждает её применимость |
| Вход отменён / Google отверг способ входа | Состояние не становится «успешно вошёл» |
| В той же сети и в близкое время донор с аккаунтом играет видео, а анонимный NewPipe получает требование входа | Наша авторизованная реализация получает и играет то же видео; иначе фиксируется конкретная недостающая зависимость |
| Истёкшие credentials | Понятное предложение повторного входа, ограниченное число запросов |
| A загружается медленно; пользователь открывает B | Поздний результат A не заменяет B |
| Выход | Credentials удалены, кеши инвалидированы, дальнейшие запросы анонимные |
| Прочие сервисы NewPipe | Google cookies в их запросы не попадают |
| Авторизованный источник нужного типа, включая SABR при его необходимости | Действительно играет через NewPlayer; наличие экрана входа не засчитывается вместо воспроизведения |
| Просмотр логов, бэкапа приложения и диагностического ZIP | Cookies, Authorization, PO-токены и подписанные URL не раскрываются |

Если проверка конкретного IP недоступна разработчику, отметить NOT RUN и передать пользователю APK и короткую инструкцию проверки. Нельзя обещать отсутствие всех блокировок YouTube.

## Что передать на следующее ревью

Полные изменённые исходники с фиксированными зависимостями; инструкция подключения/удаления модуля, команды двух вариантов сборки и их dependency graph; отдельные коммиты/патчи интеграции плеера, авторизации и необходимого Extractor; перечень перенесённых компонентов с происхождением; результат сборки и матрица PASS/FAIL/NOT RUN; известные ограничения.

В отчётах и архивах не должно быть пользовательских cookies, паролей или токенов.
