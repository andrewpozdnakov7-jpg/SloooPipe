# Остановка встроенного входа после Google 2FA

Дата: 2026-10-20. Пакет исходников: ZIP 10.
Входной материал: logcat и скриншот из `03 delivery/auth-diagnostics-fix-20261020-01`.
Персональные данные и исходный logcat не включаются в Git/архив исходников.

## Что подтверждено

Пользователь сообщил остановку внутри SloooPipe после ввода кода Authenticator.
В 16:51:48 старый logcat содержит разрешённые Google-account переходы, затем
`webview.navigation destination=OTHER allowed=false main_frame=true` и завершение
страницы без session cookie. Нет capture/result/backend событий нового входа.
Точный host/path неизвестен: прежний logger сохранял только категорию OTHER.
Скриншот показывает страницу 2FA, но не доказывает принятие кода сервером.

В нашем WebView allowlist отсутствовал `accounts.youtube.com`. Этот сервис
участвует в передаче сессии Google в YouTube через `/accounts/SetSID`:
[отчёт Google](https://bughunters.google.com/reports/vrp/BpTndJ8ut),
[сетевой trace в WebKit](https://bugs.webkit.org/show_bug.cgi?id=215845).
Это подтверждённый пропуск allowlist, но совпадение с конкретным OTHER в логе
остаётся предположением до новой записи с адресом.

## Изменения

Разрешён точный HTTPS origin `accounts.youtube.com` для браузерной навигации.
Проверка вынесена в API с тестовыми случаями поддельных hosts, userinfo и port.
Политика передачи backend credentials остаётся отдельной: только точный
`https://www.youtube.com/youtubei/v1/player`, без разрешения redirects.
Заблокированный переход показывает host в интерфейсе; статус различает Google
confirmation, перенос YouTube session и готовность ручного захвата cookies.
Ни один переход сам по себе не помечает аккаунт VERIFIED.

Диагностика DEBUG расширена по просьбе пользователя: URL routes, заголовки,
JS console, видимый текст/формы/кнопки, player payload и ошибки с причинами.
Изменения страницы отслеживаются также без навигации, каждые две секунды на экране.
Секретные значения маскируются; поля ввода не считываются.
Подробности и команда записи: [README-auth-diagnostics](../tools/README-auth-diagnostics.md).

## Что проверять на телефоне

Снять logcat от открытия окна до прохождения 2FA и результата. При остановке
оставить окно активным несколько секунд. При успехе захватить сессию и отдельно
проверить аккаунт и воспроизведение. Отказ Google принимать embedded browser
этой правкой не объявляется решённым. WSL builder не изменён.

Локально: только Java/JS/XML синтаксис, Checkstyle и проверка diff/архива.
Компиляция, JUnit и новая попытка входа на устройстве здесь не выполнялись.

## Подтверждение по logcat ZIP 10: GDS

Новый файл `logcat_2026-10-20_17-38-02.txt` находится в delivery ZIP 10.
В нём 421 блок нашего тега, 15 событий навигации и ровно один заблокированный
переход. В 17:35:23 и 17:35:44 история переключилась на `/v3/signin/rejected`;
снимки показывают предупреждение Google о небезопасном браузере/приложении.
После повтора в 17:36:45 появился password challenge, затем selection/TOTP.
В 17:37:24 последовательность стала `CheckCookie` → `ServiceLogin` →
`https://gds.google.com/web/landing`, где **наша Activity вернула запрет навигации**.
Это точный адрес из нового лога, а не предположение об `accounts.youtube.com`.

Сервис [GDS](https://gds.google.com/web/landing) открывается как Google Account.
Его конкретное содержимое после входа неизвестно: приложение заблокировало загрузку.
В ZIP 11 точный HTTPS origin `gds.google.com` добавлен в браузерный allowlist
и категорию GOOGLE_ACCOUNT; правила backend credentials не изменены.
Расширены существующие проверки разрешённого host и поддельных адресов/портов.

В логе нет capture/result/backend нового входа. Восстановленный при запуске
CAPTURED относится к старому хранилищу, не доказывает успешность новой попытки.
Переход с TOTP на CheckCookie согласуется с прохождением этого шага, но завершённая
авторизация YouTube не подтверждена. Нет оснований считать текущую остановку
блокировкой IP: в записи явный запрет конкретного перехода кодом приложения.

Предупреждение о браузере — отдельная проблема: Google
[может отклонять встроенные браузеры](https://support.google.com/accounts/answer/7675428?hl=ru).
Почему следующий повтор в этой записи прошёл дальше, лог не раскрывает.
Разрешение GDS не является исправлением политики Google и не гарантирует вход.
Для ZIP 11 здесь выполнены только статический разбор/Checkstyle и проверки ZIP;
компиляция, JUnit и проверка на телефоне не запускались. Builder и DEBUG tracing
остаются прежними. Нужна новая запись до возврата в YouTube и захвата сессии.

## Белая страница по logcat ZIP 11: региональный SetSID

В `logcat_2026-10-20_17-52-27.txt` из delivery ZIP 11 обнаружен другой
реальный маршрут. После TOTP в 17:52:10 началась `accounts.google.com/CheckCookie`,
а затем код приложения заблокировал main-frame переход на
`https://accounts.google.ru/accounts/SetSID` (`allowed=false`).
Последний снимок CheckCookie имеет `ready=complete`, пустой видимый текст и
пустой список кнопок. Это согласуется с сообщением о белом экране: промежуточная
страница не смогла закончить перенаправление. Структурированных HTTP/SSL/network
или renderer-error событий в этом файле нет.

При этом два page_finished события уже показывают
`session_cookie_present=true` для cookies `www.youtube.com`. Это прогресс
относительно предыдущей записи, но не подтверждение полного входа:
нет нового capture/result и запроса проверки аккаунта/воспроизведения.

ZIP 12 разрешает региональные account-hosts по зафиксированному
[официальному списку доменов Google](https://www.google.com/supported_domains).
Снимок получен 2026-10-20: 187 доменов; SHA256 исходного ответа
`ba827017007f54b698de62a5e3bb290327c12ddc0f9c88503511725c0baf3c49`.
Список встроен в GoogleAccountDomains, не загружается во время входа.
Разрешены только точные `accounts.<домен из списка>`, с HTTPS, без userinfo и
с портом по умолчанию/443. Это не wildcard для любых google-подобных сайтов,
не разрешение всех поддоменов Google и не изменение backend credential policy.

На account-странице при наличии валидных session cookies теперь появляется
подсказка: если страница остановилась, нажать «Передать сессию приложению» для
перехода на мобильный YouTube; после загрузки нажать снова для явного захвата.
Такой переход уже выполнялся существующей кнопкой. Автоматический захват или
присвоение VERIFIED не добавлены. Расширенная DEBUG-диагностика сохранена.

Локально выполнены Java/JS/XML static checks и Checkstyle. Сборка, JUnit и новый
вход на устройстве не запускались. WSL builder прежний. Исходники остаются
локальными: на GitHub разрешены только README и LICENSE.
